    Ferry is a standalone package. Full transfer saves through Umbraco's native services, so other packages' save handlers see Ferry's changes as normal saves. Its backoffice lives in Settings → Synchronisation → Ferry. Schema and media changes are applied to the destination's live definitions/files; content publication is a separate operation. Preserve a site/database backup appropriate to your hosting environment when operating on a real site.

    Selected transfers and operational limits¶

    Full mode implements IScopedSyncExportStore: a nonempty root selection resolves its source closure before serializing content/schema or opening media files. Unrelated source content and media are excluded from this path. Full mode also implements IScopedSyncDestinationStore: selected preview/apply reads existing destination entities in that closure and any external direct prerequisites, without serializing unrelated destination content or media. Adapters without either optional capability retain the full snapshot path. Looking up a Language root by its portable key may enumerate serializer-derived language identities because those keys differ from native CMS language GUIDs.

    Selected destination preview/apply fingerprints that bounded destination snapshot. Edits to an incoming entity or its external prerequisite invalidate approval; unrelated destination edits do not. Schema alias collisions and non-destructive shared-schema checks still run for every incoming schema during preview and again at apply. Invalid entities inside the selected source closure also continue to reject the transfer.

    An optional asset-availability extension lets a peer report, through an authenticated bounded probe, whether its staging store already contains the expected hash and length. Push, Pull and generic typed clients skip repeat network GET/PUT bytes only when that capability is advertised and the staged asset verifies. Older peers receive the normal full transfer. Full descriptors remain in the manifest, approval fingerprint and recovery records. Target media is still exported and staged locally during planning; this optimization saves network bytes, not local export work. Cache eviction causes a safe full transfer.

    For selected transfers, recovery records keep the before-state from the same bounded destination snapshot. The optional recovery journal remains limited to 64 MiB per record by default; it does not provide atomic rollback. Full-snapshot behavior remains for adapters that do not implement the optional scoped destination capability.

    Full mode can optionally limit Content variant transfer to selected cultures. The frozen manifest carries the scope and the approval fingerprint covers it. The transfer includes selected variant names and values plus invariant values, while preserving destination variants outside the selection. A Pull peer that does not advertise this capability is rejected before export. Creating a scoped culture-variant item requires the default and all mandatory cultures. The Content transfer modal provides an optional localized culture-code input; empty means all cultures, and review shows the selected scope. Media transfer does not offer culture scope. The 12/12 browser run verifies these bounded interactions, not full UI parity.

    The selected closure includes required ancestors, schemas and referenced entities. Those dependencies can be planned as updates, not only creations. Review the full plan rather than assuming that only the explicitly selected branch will change.

    An administrator can opt into an existing Content or Media parent change by setting allowMoves: true on a Push or Pull preview. The Full destination must explicitly enable Ferry:Full:AllowExistingTreeMoves and advertise the negotiated existing-tree-move capability. Approval binds the move choice and target branch state; applying stale approval rejects before mutation. A native move carries the entire existing subtree, including destination-only descendants. It can affect a published path, but transfer still does not request publication. The Content/Media transfer modals and Settings dashboard expose a default-off move toggle.

    Tree trash is deliberately separate from transfer reconciliation. An administrator selects one to 100 explicit, unique Content or Media roots on the destination; roots may not overlap, may not already be recycled, and may not be top-level roots. The Full destination must set Ferry:Full:AllowExistingTreeTrash to true, which is false by default. The receiver exposes separate TrashPreview and TrashApply peer-policy operations, so a peer permitted to transfer, browse, or preview another operation is not thereby permitted to trash. Delegated editor grants do not authorize tree trash.

    Preview shows each selected root's path, the complete descendant impact and the number of published descendants. Its 15-minute, owner-bound, single-use approval freezes the selected branch, its ancestors and relevant publication state; a changed, missing, moved, or otherwise unsafe branch causes apply to reject as stale before a native recycle-bin move. Content with a publication schedule anywhere in the selected branch is rejected because it could publish later. The operation never infers trash from a source omission, never uses delete-missing semantics, and never empties the Umbraco recycle bin.

    Before applying, the receiver records the bounded before-state in its tree-trash journal and returns the correlated operation ID with the outcome. That record supports manual investigation and host-specific recovery after cancellation, interruption or partial completion. It is not an atomic rollback and does not automatically restore prior published versions, files, or a whole site. Inspect the destination recycle bin and the correlated journal record before retrying an unknown outcome.

    Peers expose an authenticated, no-store capability declaration for protocol/schema version, adapter identity, supported kinds, operations and effective limits. A transfer checks it before source export or asset staging, and rechecks it before apply. Full and DraftText use distinct transfer formats, so they cannot transfer content to one another. Publication has its own advertised operations and approval.

    Source-scoped selection, bounded destination planning reads, capability negotiation and optional Full-mode culture-scoped transfer are implemented. The Content transfer modal exposes optional culture scope; Media does not. Further planning-time media optimization to avoid local re-export remains roadmap work.

    Published source-version selection is a distinct Full-mode option. For variant Content, the source's current PublishedCultures determine the effective culture scope: each published culture transfers its name, template and published value for each segment. Draft values in destination cultures outside that scope persist. A selected culture that is not published at the source rejects the request. Full-site selection omits unpublished nodes and fails closed if an omitted unpublished ancestor is required by a selected published node. Draft is the default source version. A Published source version is applied as a destination draft; making it live requires the separate destination publication workflow. The version capability is negotiated before export, so peers that do not advertise it reject Published requests.     Source tree enumeration uses pages internally, but the transfer still builds and a whole manifest. Ordinary transfer has no paged protocol, resumable upload or background continuation. The queue never automatically retries, rolls back, cancels, resumes assets, or replays interrupted work, and it is private to one process rather than a distributed queue. These bounds are not a tested large-site capacity claim.

    Named receiver policies¶

    A receiver may keep one optional legacy bearer token, which grants all receiver operations, or configure named peers with an id, rotation tokens, enabled flag, revision, and explicit operation allow-list. Named peers scope only the receiver machine credential; they do not implement user-group, content-root, or culture authorization. The available operations are capabilities, export, preview, apply, asset read, asset write, publication preview, publication apply, recovery read, browse, and BrowseSearch. BrowseSearch is absent from the default capabilities response and is advertised only when the caller explicitly requests the extension.

    AddFerryTransportFromConfiguration reads named-peer policy for each request after the host publishes a configuration reload. Invalid current policy values fail closed; request and asset limits remain startup settings. An operator must advance a peer revision for every policy change. Named transfer/publication approvals are HMAC-protected, process-local envelopes that expire after 15 minutes; a restart, scale-to-zero or another instance invalidates them and apply answers 410 Gone; run one receiver instance. They are not a replay ledger or a general single-use token. See the peer-policy contract.

    User-group permissions for delegated editors¶

    Ferry registers two Umbraco permission verbs, Send with Ferry (CommunitySync.Push) and Receive with Ferry (CommunitySync.Pull). Administrators assign them in the Users section, per document (granular permissions) or as a group default. Umbraco has no media granular permissions, so media transfers use the group default. A delegated editor needs the verb in addition to the configured grant and Umbraco's native permissions; the verb never replaces either. Administrators are unaffected.

    Ferry:Backoffice:RequireGranularPermissions (default true) can switch the verb check off. On the first start after upgrading, every user group already configured in DelegatedEditors receives its direction's verb as a default permission, so existing grants keep working. That step runs once, so a verb an administrator later removes is never restored. Groups configured after that first start need the verb assigned in the Users section.

    Administrator pull¶

    An authenticated administrator may use the management pull preview/apply API only for a configured connection whose server-side AllowPull flag is true. Preview accepts either a full site or 1–1000 typed roots, exports the source closure, stages verified assets, and freezes an owner-bound 15-minute approval. Apply consumes the approval, rechecks source/local capabilities and connection state, and writes drafts through the same local recovery journal used by receiver apply. It does not publish, delete, schedule, or create a durable job.

    The optional Browse reader lists configured remote roots, including nested roots, as a virtual paged list and accepts pages of 1–100 items. It returns key, name, human-readable breadcrumb, child presence, and cultures. It resolves breadcrumb labels with one bounded public ancestor lookup per page (at most the trailing 16 IDs per item); an ellipsis marks a shortened breadcrumb. It does not expose native integer paths, properties, serialized payloads, snapshots, or media bytes. Sibling order uses native sortOrder; equal-order ties and concurrent sibling changes have no stronger pagination guarantee. A 3 MiB typed-client response ceiling bounds the largest legal escaped JSON page.

    The management Browse route requires an HTTPS configured AllowPull source and the existing pull compatibility preflight: source Browse plus Export, local Preview plus Apply, matching format, and the requested kind. The source machine permission remains separate: a named peer may be granted Browse without Export. Delegated child navigation verifies remote ancestry and each returned direct child before exposing metadata. The optional BrowseSearch route repeats the same source, local, delegated and ancestry checks, then searches only entity names in the permitted Content or Media scope. Terms must be 2–128 characters, SQL wildcard characters %, _ and [ are rejected, results are metadata-only and pages contain at most 50 items; the maximum offset is 10,000. It does not query property values, serialized data, media bytes, or a general site index. Administrator previews can show bounded field differences for supported Content/Media values; delegated preview responses suppress them. Delegated Pull grants can scope permitted remote roots and cultures and must pass native permissions; they cannot request a full-site pull or schema changes. The feature remains experimental and is not production-ready.

    Explicit exclusions and fail-closed behavior¶

    The tested subset is not a claim that every property editor, reference type or Media configuration transfers. Unsupported values reject before writes:

    • Culture-varying Media outside the tested name/caption/umbracoFile shape. The tested names survive through Ferry's private durable store, rather than native Umbraco's fresh Media read; arbitrary culture-varying Media editors and native Backoffice display of those names are not implied. Segment-varying scalar Media values are covered only for the tested TextBox contract.
    • Published-source Content UploadField transfer is limited to publications with a matching immutable publish-time snapshot. Missing, corrupt, preexisting, or raw-value-mismatched snapshots fail closed. New native SaveAndPublish content preserves its pre-version immutable capture and binds it only after publication assigns a matching PublishedVersionId. Draft-source transfer uses hash-addressed descriptors and exact destination-byte verification. SQL Server source validation proves the new snapshot table, primary key, and one saved snapshot row; a SQL Server target culture-Media run proves table/primary-key creation with no snapshot rows expected. The tested culture-varying shape covers an en-US-only republish carrying an untouched fr-FR snapshot forward. Arbitrary culture-varying UploadField configurations, multi-node hosting, hosted CI, production topology, and every other Content file editor remain untested.
    • Arbitrary relational Media properties/editors. The tested relational mapping is MediaPicker3 and destination Media identity; it does not imply support for every relation editor or configuration.
    • Unknown or custom editors unless the host explicitly registers and validates a scalar contract or a mapped contract with an installed mapper.
    • User and Member references. Supported references are the tested Content/Media pickers, Block List dependencies and rich-text links/images; this does not cover arbitrary relation types or every editor configuration.
    • Template files and template hierarchies, unless both peers opt into executable template transfer (see Optional modules). Otherwise a matching template must already be installed at the destination for an assignment to be retained.
    • Existing schema changes that need storage or variation migration, property removal, and composition removal. Missing compatible schemas can be created, but unsupported changes need an explicit host migration.

Umbraco's system relation types (reference tracking, relate-on-copy/delete) are never transferred. A relation's identity is derived from (type, parent, child), so repeats are Unchanged and an existing identical destination relation is matched whatever its local key; relations are added or their comment updated, never deleted.     Bulk apply suspensions On by default; Ferry:Full:BulkApply:Suspensions (None, ScheduledPublishing, Examine, DocumentCache, All) and MinimumOperations (default 50) A Full batch with at least MinimumOperations operations pauses scheduled publishing, Examine indexing and document-cache refresh through Umbraco's Suspendable switches, then resumes them once on every exit path (success, failure, cancellation). Resuming Examine after a suspended index request rebuilds all indexes, which is why small batches keep per-item indexing. Overlapping batches share one reference-counted suspension; a failing resume is logged and does not block the others. The switches are process-local, so other load-balanced instances are unaffected. Local negotiation only; no peer capability. Unit tests; packages 3/3 with MinimumOperations=1 (target log shows suspend and resume of All)
    Server-side transfer queue Every backoffice user with Ferry access; GET/PUT community-sync/queue Each user's queue (at most 1000 Content, Media, DocumentType, MediaType or DataType roots) is stored on the server in cmsCommunitySyncQueue, one row per user, created by its own CommunitySync.TransferQueue migration plan. The queue follows the user across browsers and is cleared after a completed transfer as before. The browser keeps a synchronous cache: the server copy replaces it when the backoffice loads, a browser queue from before is uploaded once, and a server without the endpoint keeps the browser-only queue. Queued Content and Media show a "Queued for transfer" sign in trees and collections (CommunitySync.QueuedForTransfer flag); the sign appears when the tree is next loaded. Queueing grants nothing: every transfer is still authorized at review. queue 1/1
    Content-only sites Off by default; Ferry:Full:ContentOnly on the receiving site For sites whose schema is deployed with the code, for example code-first migrations or schema files in source control.     Schema storage and migrations¶

    Where schema is deployed with the code, set Ferry:Full:ContentOnly on the receiving site so transfers carry content only (see the modules table).

    Data type exports declare native storage metadata. Apply preserves that declared storage instead of normalizing to the editor's default storage. Existing shared data type editor or storage changes are blocked before mutation because they can affect destination-only content, unless Umbraco reports that no stored value uses the data type (for example a fresh site's built-in types); a data type used by an element type always counts as used. The same applies to changing or removing a property. Property removal, storage/variation changes, composition removal and other unsupported schema migrations require an explicit migration. Older experimental manifests without storage metadata must be exported again with the current version.

    Custom property editors¶

    Unknown custom editors fail closed. Declare verified behavior explicitly:

    umbraco.AddFerryUmbracoFull(options =>
{
    options.ScalarEditors.Add("Custom.PlainText");
    options.MappedEditors.Add("Custom.Relations");
});

    Use a scalar contract only for values that contain no site-local IDs, file paths or entity references. A mapped contract additionally requires an installed value mapper for the editor. The adapter checks mapped round trips and declared references before saving content; declaring an alias does not create a mapper automatically. Validate your custom editor on two disposable sites with different local IDs.

    Explicit publication¶

    Publication selects destination content keys and cultures, obtains a fresh publication preview, then requires its fingerprint in a separate apply request. A sole * explicitly requests every currently available culture; invariant content also uses *. Specific culture selections remain specific. An unpublished ancestor must be explicitly selected where supported or published separately. An invariant child beneath an unpublished culture-variant ancestor requires that ancestor to be published first. Publication schedules must be handled separately.

    The service validates properties and checks current draft/schema/ancestor and language configuration state. Missing mandatory cultures must already be published or explicitly selected; they are never silently added. It does not infer source publication, publish unselected ancestors, unpublish, change schedules or perform an automatic rollback. Completed items stay published if a later item fails. OutcomeUnknown means a native call may have changed that item before throwing; inspect its state before obtaining a new preview.

    Recovery and concurrency¶

    The optional journal writes the selected destination draft before-state (or the full snapshot for adapters without scoped planning), attempted operation and approved fingerprint before mutation, followed by an independent outcome. A missing outcome means completion is unknown. Publication recovery contains draft state, not a copy of every previous published version; it cannot reverse publication. Assets referenced by recovery records must remain in the configured asset store. Retention and site/database backups remain host responsibilities.

    One operation gate covers the following:

    • inbound sync
    • backoffice source export and planning
    • Pull, package and snapshot apply
    • durable jobs

    Where the backoffice package is installed, the gate also holds a cluster-wide lease while each operation runs. The lease is a single cmsCommunitySyncLease row in the Umbraco database, so instances that share the database run one Ferry operation at a time. The lease works as follows:

    • An instance claims it with a conditional update and renews it every 30 seconds.
    • Claiming waits until the lease is free. If the caller's request is canceled, it gives up without taking the lease.
    • An instance that stops without releasing the lease loses it after two minutes.
    • Expiry uses each instance's UTC clock, so keep instance clocks synchronized.

    A receiver-only host without the backoffice package keeps the process-local gate.

    Preview fingerprints reject changes before application. Neither safeguard locks external CMS editors or other writers for the entire operation. Use appropriate operational coordination for actively edited sites.

    There is no implicit deletion, account replication, executable template/script deployment, or guarantee that every third-party editor works without an adapter.
